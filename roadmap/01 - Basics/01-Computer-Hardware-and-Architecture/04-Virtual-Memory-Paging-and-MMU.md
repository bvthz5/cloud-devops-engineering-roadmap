# 04 - Virtual Memory, Paging, TLB & MMU

---

## 1. Why Virtual Memory? (The Isolation Problem)

In early computing systems, programs executed directly against physical RAM addresses. If Program A wrote data to address `0x00100000`, and Program B inadvertently wrote to that same address, Program A crashed or suffered silent data corruption. Furthermore, programs were constrained to the physical size of RAM.

Modern operating systems solve this fundamentally using **Virtual Memory**:
1. **Process Isolation:** Every process is granted its own private, isolated virtual address space (up to 16 Exabytes on 64-bit systems). A process cannot see or touch another process's memory.
2. **Memory Overcommitment:** The operating system can allocate more memory to running processes than physically exists in hardware by utilizing paging and secondary storage (swap).
3. **Contiguous Virtual Mapping:** Programs observe contiguous blocks of memory, while the underlying physical RAM pages can be scattered, fragmented, or mapped to files.

---

## 2. Virtual Address vs. Physical Address

- **Virtual Address:** The memory address generated by the program instruction (e.g., in a pointer variable in C/Go).
- **Physical Address:** The actual hardware electrical address sent across memory bus lines to the physical DRAM chips.
- **The Hardware Translator:** The **Memory Management Unit (MMU)** is a dedicated hardware component inside the CPU core that translates every virtual address into a physical address in real time.

```text
CPU Core executes: `mov rax, [0x7ffeefbff4a0]` (Virtual Address)
                         │
                         ▼
        ┌─────────────────────────────────┐
        │  Memory Management Unit (MMU)   │
        │  Translates Virtual ➔ Physical  │
        └────────────────┬────────────────┘
                         │
                         ▼
Physical Bus sends: `Read RAM at 0x1a403000` (Physical Address)
```

---

## 3. Memory Pages & Page Frames

Virtual memory and physical RAM are not mapped byte-by-byte; they are mapped in standardized chunks:
- **Virtual Page:** A fixed-size block of virtual address space (standard architecture size: **4 Kilobytes / 4096 bytes**).
- **Physical Page Frame:** A fixed 4 KB block of physical DRAM.
- **Huge Pages:** Modern Linux supports 2 Megabyte and 1 Gigabyte "HugePages" to reduce TLB cache miss overhead for massive database workloads (PostgreSQL, MySQL, Redis, Java heaps).

---

## 4. Multi-Level Page Tables

To map virtual pages to physical page frames, the operating system maintains a tree data structure called the **Page Table**. On 64-bit systems (x86-64 4-level paging), a 48-bit virtual address is decomposed into table indices:

```text
48-Bit Virtual Address:
┌──────────────┬──────────────┬──────────────┬──────────────┬──────────────┐
│ PML4 Index   │ Directory Ptr│ Directory    │ Page Table   │ Byte Offset  │
│ (9 bits)     │ (9 bits)     │ (9 bits)     │ (9 bits)     │ (12 bits)    │
└──────┬───────┴──────┬───────┴──────┬───────┴──────┬───────┴──────┬───────┘
       │              │              │              │              │
       ▼              ▼              ▼              ▼              │
    [CR3] ──> PML4 ──> PDPT ───> Page Dir ──> Page Table           │
                                                   │               │
                                                   ▼               ▼
                                         Physical Page Base + Offset = Physical Address
```
- **Control Register 3 (CR3):** The CPU register holding the physical memory pointer to the currently running process's root page table (PML4).
- **Context Switch Mechanism:** When the OS scheduler switches processes from PID 100 to PID 200, it updates the `CR3` register. Immediately, the entire virtual memory landscape shifts to the new process!

---

## 5. Translation Lookaside Buffer (TLB)

Walking a 4-level page table requires **four separate DRAM memory lookups** just to locate the physical address of a single byte—a 400 ns penalty that would ruin system performance.

The **TLB (Translation Lookaside Buffer)** is an on-die high-speed associative hardware cache that stores the most recent **Virtual Page $\rightarrow$ Physical Page Frame** translations.

```text
Virtual Address requested by CPU
               │
               ▼
      Is translation in TLB?
       ├── HIT  ──> Instant Physical Address (< 1 ns)! Pipeline continues.
       └── MISS ──> Hardware Page Table Walker reads PML4/PDPT/PD/PT from DRAM (60-100 ns).
                    Populates TLB with new translation.
```

---

## 6. Page Faults (Major vs. Minor)

A **Page Fault** is an interrupt raised by the CPU hardware MMU when a program accesses a virtual page that cannot immediately be mapped to physical RAM.

### 1. Minor Page Fault (Soft Fault)
- The requested page is already resident in RAM, but the MMU page table has not yet created the translation entry.
- *Examples:* First write to memory allocated via `malloc()` (Demand Paging), or Copy-on-Write (`fork()`).
- *Latency:* Fast (~few microseconds); resolved by kernel updating the page table entry without disk I/O.

### 2. Major Page Fault (Hard Fault)
- The requested page is **NOT in physical RAM**; it was swapped out to persistent disk storage (Swap partition/file) or represents an uncached memory-mapped file (`mmap`).
- *Process:* The CPU freezes the thread, the kernel triggers disk I/O to read the 4 KB page into an empty physical RAM frame, updates the page table, and restarts the instruction.
- *Latency:* Extremely slow (10 to 50 microseconds on NVMe, 5 to 10 milliseconds on HDD). Frequent major page faults cause catastrophic system lag known as **Thrashing**.

---

## 7. Memory Protection Bits (Security Boundaries)

Every page table entry stores hardware permission control flags enforced directly by the CPU:
- **Readable (R) / Writable (W):** Prevents read-only memory (e.g., application code `.text` segment or string literals) from being overwritten.
- **User / Supervisor (U/S):** Prevents unprivileged user space applications (Ring 3) from accessing kernel data structures (Ring 0). Attempted violations trigger immediate hardware trap: **Segmentation Fault (`SIGSEGV`)**.
- **NX Bit (No-Execute / XD / DEP):** Marks data areas (such as the Call Stack and Heap) as strictly non-executable. If malicious input attempts to inject shellcode into a buffer on the stack, the CPU refuses to execute it, blocking buffer overflow exploits.
