## 📌 Scenario 7: SLO Multi-Window Multi-Burn-Rate Alerting Triggers Correctly on Slow Latency Degradation

### 🚨 The Production Scenario
An e-commerce checkout API degrades slowly: 99th percentile latency increases from 200ms to 1200ms, slowly exhausting the 99.9% monthly error budget. Traditional threshold alerts (which check for >5% error spikes over 5 minutes) completely miss the incident.

### 🔬 Root Cause Analysis (RCA) & Deep Mechanics
The team relied on naive short-term threshold alerts that detect sudden massive outages but fail to detect slow, insidious SLA burns that deplete error budgets over hours.

### 🛠️ Step-by-Step Triage & Troubleshooting Workflow
- Implement Google SRE Multi-Window Multi-Burn-Rate alerting rules in Prometheus.
- Define Service Level Objectives (SLOs) and Error Budgets (e.g., 99.9% availability over 30 days = 0.1% budget).
- Calculate burn rates: 14.4x burn rate (consumes 2% budget in 1 hour) alerts PagerDuty within 2 minutes; 6x burn rate (consumes 5% budget in 6 hours) alerts within 15 minutes.
- Require both short window (e.g., 5m) and long window (e.g., 1h) to exceed the burn rate threshold simultaneously to prevent flapping.
- Standardize SLO definitions using Sloth or Pyrra to generate Prometheus rules automatically.

### 💻 Exact Diagnostic & Remediation Commands
```bash
# Validate multi-window burn rate alert rules
promtool check rules /etc/prometheus/rules/slo_burn_rates.yml

# Query current 1-hour error budget burn rate
curl -s 'http://prometheus:9090/api/v1/query?query=slo:error_budget:burn_rate_1h'

# Inspect PrometheusRule CRD generated by Sloth
kubectl get prometheusrule slo-checkout-burn-rates -n monitoring -o yaml

# Check active burn rate alerts in Alertmanager
amtool alert list --filter 'alertname=CheckoutErrorBudgetFastBurn'

```

### 🗣️ Ideal Interview Candidate Answer (Verbal Pitch)
> "Threshold alerts are obsolete because they are either too sensitive or completely blind to slow burns. I implement Google SRE multi-window multi-burn-rate alerting. By correlating a short window and a long window simultaneously, we catch rapid burns in 2 minutes and slow burns in 15 minutes, with zero noise and mathematically guaranteed error budget protection."

## 📌 Scenario 8: Blackbox Exporter External Probing Detects Edge CDN Routing Loop

### 🚨 The Production Scenario
Internal Kubernetes metrics and pods report 100% healthy, green status. However, customers in Europe and Asia report they cannot reach the website, receiving Cloudflare 522 Origin Connection Timeouts.

### 🔬 Root Cause Analysis (RCA) & Deep Mechanics
An edge DNS update or CDN origin rule pointed to a decommissioned external load balancer IP. In-cluster whitebox monitoring was blind to this because inside the cluster, the services were healthy.

### 🛠️ Step-by-Step Triage & Troubleshooting Workflow
- Deploy Prometheus Blackbox Exporter across multiple geographic public regions (outside the production VPC).
- Configure HTTP probes testing end-to-end user connectivity, TLS certificate validity, and HTTP status codes.
- Verify external DNS resolution across public resolvers (8.8.8.8, 1.1.1.1).
- Correct CDN origin routing and DNS records.
- Establish alert rules on `probe_success == 0` with geographic dimension tags.

### 💻 Exact Diagnostic & Remediation Commands
```bash
# Execute manual blackbox probe inspection
curl -s 'http://blackbox-exporter:9115/probe?target=https://www.example.com&module=http_2xx'

# Trace external DNS delegation and resolve target IP
dig +trace www.example.com @8.8.8.8

# Test direct HTTP handshake to CDN edge IP
curl -Iv https://www.example.com --resolve www.example.com:443:203.0.113.10

# Inspect blackbox exporter probe logs
kubectl logs -l app.kubernetes.io/name=prometheus-blackbox-exporter -n monitoring

```

### 🗣️ Ideal Interview Candidate Answer (Verbal Pitch)
> "Internal whitebox metrics tell you if your software is running; external blackbox monitoring tells you if your users can actually use it. When edge CDNs or DNS misroute, internal metrics remain green while users suffer. I deploy Blackbox Exporter in multiple external regions to probe public endpoints every 30 seconds, catching perimeter routing and SSL failures immediately."

## 📌 Scenario 9: Jaeger Distributed Tracing Ingestion Overload - Sampling Rate Tuning

### 🚨 The Production Scenario
Jaeger collector Cassandra/Elasticsearch storage costs surge to $15,000/month, and storage clusters experience severe disk I/O saturation, causing Jaeger collectors to drop 40% of spans.

### 🔬 Root Cause Analysis (RCA) & Deep Mechanics
Microservices were configured with 100% constant sampling (`sampler.type=const, param=1`), sending millions of mundane health check and static asset traces to Jaeger storage.

### 🛠️ Step-by-Step Triage & Troubleshooting Workflow
- Migrate from client-side constant sampling to Adaptive Sampling or Remote Sampling via OpenTelemetry Collector.
- Implement Tail-Based Sampling in the OpenTelemetry Collector: buffer all spans in memory and only persist traces that contain HTTP 5xx errors, exceptions, or latency exceeding the 95th percentile.
- Drop health check routes (`/healthz`, `/metrics`, `/ready`) from trace collection completely.
- Set probabilistic sampling for mundane 200 OK requests (e.g., sample 1% of successful transactions).
- Reclaim storage disk capacity and verify 100% capture of error traces.

### 💻 Exact Diagnostic & Remediation Commands
```bash
# Check dropped spans in Jaeger collector
curl -s http://jaeger-collector:14269/metrics | grep jaeger_collector_spans_dropped_total

# Inspect tail-based sampling rules in Otel Collector
kubectl get opentelemetrycollector -n monitoring -o yaml | grep -A 10 tail_sampling

# Verify trace retrieval via Jaeger query API
curl -s http://jaeger-query:16686/api/traces?service=checkout&limit=5

# Clean up old Elasticsearch tracing indices
es-curator --config /etc/curator.yml delete_indices_older_than 7d

```

### 🗣️ Ideal Interview Candidate Answer (Verbal Pitch)
> "Storing 100% of distributed traces is a massive waste of money and storage I/O because 99% of requests are successful, uninteresting transactions. I implement Tail-Based Sampling in the OpenTelemetry Collector. We inspect the trace after completion: if it contains an error or high latency, we store 100% of it. If it's a routine 200 OK, we sample just 1%, cutting storage costs by 85% while retaining every critical bug trace."
