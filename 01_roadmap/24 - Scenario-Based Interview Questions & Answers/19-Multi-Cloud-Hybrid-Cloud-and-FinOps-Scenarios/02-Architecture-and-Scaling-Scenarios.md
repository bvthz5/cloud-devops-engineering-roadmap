## 📌 Scenario 4: AWS Savings Plans & Reserved Instances (RI) Underutilization & Mismatch

### 🚨 The Production Scenario
An enterprise commits to $100,000/month in 3-year EC2 Reserved Instances for standard `m4.xlarge` instances. Six months later, the engineering team migrates all microservices to Graviton ARM64 (`c6g.xlarge`) and Kubernetes Fargate, leaving $60,000/month of RIs completely unused.

### 🔬 Root Cause Analysis (RCA) & Deep Mechanics
The procurement team purchased rigid Standard EC2 Reserved Instances tied to a specific instance family and OS, without consulting the engineering roadmap that planned a major architecture migration.

### 🛠️ Step-by-Step Triage & Troubleshooting Workflow
- Audit current RI/Savings Plans utilization using AWS Cost Explorer RI Utilization & Coverage reports.
- Sell unused Standard RIs on the AWS Reserved Instance Marketplace to recover capital.
- Transition future commitments from rigid Standard RIs to Compute Savings Plans (which automatically apply across EC2, Fargate, and Lambda regardless of instance family, region, or OS).
- Establish a cross-functional FinOps committee aligning cloud procurement with engineering roadmap milestones.
- Target 70-80% coverage with Savings Plans, maintaining 20% on-demand flexibility to prevent over-commitment.

### 💻 Exact Diagnostic & Remediation Commands
```bash
# Query EC2 Reserved Instance utilization percentages
aws ce get-reservation-utilization --time-period Start=2026-09-01,End=2026-09-30

# Query Compute Savings Plans utilization and coverage
aws ce get-savings-plans-utilization --time-period Start=2026-09-01,End=2026-09-30

# List active RI marketplace sale listings
aws ec2 describe-reserved-instances-listings

# Generate data-driven Compute Savings Plans recommendation
aws ce get-savings-plans-purchase-recommendation --savings-plans-type COMPUTE_SP --term-in-years ONE_YEAR --payment-option NO_UPFRONT

```

### 🗣️ Ideal Interview Candidate Answer (Verbal Pitch)
> "Standard RIs lock you into specific instance families, making them an anti-pattern for agile teams migrating architectures. I standardize on Compute Savings Plans, which flexibly apply across any EC2 instance family, AWS Graviton, Fargate, and Lambda. Furthermore, we cap commitment at 75% of baseline usage to preserve elastic headroom for architectural pivots."

## 📌 Scenario 5: Multi-Cloud Identity Federation (OIDC) Token Failure Locks Out CI/CD Pipelines

### 🚨 The Production Scenario
GitHub Actions workflows attempting to deploy infrastructure to both AWS and Azure using OpenID Connect (OIDC) fail simultaneously with `Invalid Identity Token: Audience or Subject mismatch`.

### 🔬 Root Cause Analysis (RCA) & Deep Mechanics
The GitHub organization renamed a repository or altered the default branch from `master` to `main`. The AWS IAM OIDC Trust Policy and Azure Federated Identity Credential strictly validated the `sub` claim string (`repo:org/repo:ref:refs/heads/master`), causing cryptographic token verification to fail.

### 🛠️ Step-by-Step Triage & Troubleshooting Workflow
- Inspect the raw OIDC token claims generated by GitHub Actions (`actions/id-token`).
- Verify the Subject claim (`sub`) string in the IAM Role Trust Policy in AWS and Federated Credential in Azure.
- Update the IAM Trust Policy to reflect the new repository name and branch pattern (`repo:org/repo:ref:refs/heads/main` or wildcard `*`).
- Ensure the Audience (`aud`) claim matches `sts.amazonaws.com` and `api://AzureADTokenExchange`.
- Verify pipeline deployment resumes without static access keys.

### 💻 Exact Diagnostic & Remediation Commands
```bash
# Inspect AWS IAM OIDC Role Trust Policy document
aws iam get-role --role-name GitHubActionsDeployRole --query 'Role.AssumeRolePolicyDocument'

# List Azure AD Federated Identity Credentials and subject mappings
az ad app federated-credential list --id <AZURE_CLIENT_ID>

# Verify absence of static long-lived credentials in GitHub repository
gh secret list

# Test manual OIDC token exchange via AWS CLI
aws sts assume-role-with-web-identity --role-arn arn:aws:iam::123:role/test --role-session-name test --web-identity-token $TOKEN

```

### 🗣️ Ideal Interview Candidate Answer (Verbal Pitch)
> "OIDC eliminates long-lived static cloud keys by verifying short-lived JWT claims directly between GitHub and the cloud provider. When token exchanges fail, it is almost always a mismatch in the Subject claim, often caused by branch renames or repository moves. I update the cloud trust policy's 'sub' claim to match the new branch context, restoring secure keyless authentication."

## 📌 Scenario 6: Cloud Cost Anomaly Detection - Rogue BigQuery Query Incurs $8,000 Bill

### 🚨 The Production Scenario
An intern runs an unpartitioned BigQuery query with `SELECT * FROM massive_clickstream_table` joining against another unpartitioned table without a LIMIT clause, scanning 160 Terabytes of data and costing $800 in 45 seconds.

### 🔬 Root Cause Analysis (RCA) & Deep Mechanics
BigQuery on-demand pricing charges $5 per TB scanned. The query executed against unpartitioned, unclustered tables without organizational query cost controls or daily quota limits.

### 🛠️ Step-by-Step Triage & Troubleshooting Workflow
- Immediately cancel any running long queries via BigQuery console or CLI.
- Enforce table partitioning (by date/timestamp) and clustering on frequently filtered columns.
- Set 'Maximum Bytes Billed' limits in BigQuery query settings and client libraries.
- Configure BigQuery Custom Cost Controls in GCP IAM: enforce daily project and user query quotas (e.g., maximum 5 TB/day per user).
- Require `dry_run` validation in development tools to preview bytes scanned before query execution.

### 💻 Exact Diagnostic & Remediation Commands
```bash
# Perform dry-run query to preview total bytes scanned before running
bq query --use_legacy_sql=false --dry_run 'SELECT * FROM `proj.dataset.clickstream`'

# Cancel runaway active BigQuery query job
bq cancel <JOB_ID>

# Enforce daily query quota limit per user
gcloud alpha bigquery quotas set --project=proj --user=intern@corp.com --quota=10TB

# Audit most expensive queries of the day
SELECT project_id, user_email, total_bytes_billed, query FROM `region-us`.INFORMATION_SCHEMA.JOBS_BY_PROJECT WHERE creation_time > TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 1 DAY) ORDER BY total_bytes_billed DESC LIMIT 5;

```

### 🗣️ Ideal Interview Candidate Answer (Verbal Pitch)
> "On-demand BigQuery can cause massive billing spikes if unpartitioned tables are scanned blindly. I mitigate this with three strict controls: first, mandate date partitioning and require partition filters on tables; second, set 'maximum_bytes_billed' flags in application queries; third, enforce BigQuery daily user quotas at the GCP organization level so no individual query or user can exceed budget limits."
