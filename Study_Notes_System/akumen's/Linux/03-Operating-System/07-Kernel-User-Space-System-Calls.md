# 07 - Dual-Mode Operation, CPU Traps & System Calls

Modern CPUs and operating systems rely on hardware-enforced **Dual-Mode Operation** to guarantee that user software cannot take down the physical machine or compromise other workloads.

---

## 1. Dual-Mode Operation & The Hardware Mode Bit

The CPU architecture maintains a hardware **Mode Bit** inside its status register:
- **`0` = Kernel Mode (Supervisor Mode):** The CPU can execute every instruction in its instruction set architecture (ISA), manipulate page tables, access all memory, and manage hardware I/O ports.
- **`1` = User Mode:** The CPU is restricted to executing non-privileged instructions. Attempting to execute a privileged instruction raises a hardware trap.

```
                  ┌───────────────────────────────┐
                  │ User Mode (Ring 3, Mode Bit 1)│
                  └───────────────┬───────────────┘
                                  │ System Call / Trap
                                  ▼ (Hardware switches Mode Bit to 0)
                  ┌───────────────────────────────┐
                  │ Kernel Mode(Ring 0, Mode Bit 0│
                  └───────────────┬───────────────┘
                                  │ Return from Trap (sysret)
                                  ▼ (Hardware restores Mode Bit to 1)
                  ┌───────────────────────────────┐
                  │ User Mode (Ring 3, Mode Bit 1)│
                  └───────────────────────────────┘
```

### Privileged vs. Non-Privileged Instructions:

| Category | Instruction Types | Execution Allowed In |
|---|---|---|
| **Non-Privileged** | Math operations (`add`, `sub`), branching (`jmp`, `call`), register data moves (`mov`). | User Mode & Kernel Mode |
| **Privileged** | Changing page tables (`mov %rax, %cr3`), halting CPU (`hlt`), enabling/disabling interrupts (`cli`, `sti`), accessing I/O ports (`in`, `out`). | **Kernel Mode ONLY** |

## 2. Interrupts, Traps & Exceptions

Control transitions from User Mode to Kernel Mode through three distinct hardware mechanisms:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        CPU EVENT CLASSIFICATION                        │
├─────────────────┬─────────────────┬────────────────────────────────────┤
│ Type            │ Synchronous?    │ Trigger Cause & Example            │
├─────────────────┼─────────────────┼────────────────────────────────────┤
│ **Hardware      │ Asynchronous    │ Generated by external hardware     │
│  Interrupt**    │ (Unpredictable) │ timer tick, network packet arrival,│
│                 │                 │ keyboard keypress.                 │
├─────────────────┼─────────────────┼────────────────────────────────────┤
│ **Software      │ Synchronous     │ Programmatically requested by user │
│  Trap**         │ (Predictable)   │ software; e.g. system calls        │
│                 │                 │ (`syscall`), debugger breakpoints. │
├─────────────────┼─────────────────┼────────────────────────────────────┤
│ **CPU           │ Synchronous     │ Generated by CPU hardware when     │
│  Exception**    │ (Fault)         │ error occurs; e.g. Divide by zero, │
│                 │                 │ Page fault, General protection.    │
└─────────────────┴─────────────────┴────────────────────────────────────┘
```

## 3. The 3 Methods of Passing Parameters to System Calls

When an application requests a system call (like `write(fd, buffer, count)`), how are the parameters passed from user space into kernel space?

1. **CPU Registers (Fastest - Standard in modern Linux):**
   Parameters are loaded directly into CPU registers (`%rdi`, `%rsi`, `%rdx`). Limited by the number of hardware general-purpose registers (up to 6 on x86_64).
2. **Memory Block / Table:**
   When arguments exceed available registers, they are stored in a contiguous block in memory, and a single pointer to that memory block is passed in a register.
3. **Stack:**
   Arguments are pushed onto the process's stack by user code, and popped off by the kernel trap handler.
